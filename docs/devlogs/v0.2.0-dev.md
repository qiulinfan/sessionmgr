# Session Manager v0.2.0-dev Devlog

> Status: Superseded by v0.3.0-dev on 2026-08-05
> Date: 2026-07-30

## Objective and scope

Plan and implement a local desktop GUI that lets developers inspect and accept
Session Manager's capture, verify, restore, handoff, and sync behavior without
memorizing CLI commands.

The target scope is macOS and Linux, a Wails v2 desktop shell, a
React/TypeScript frontend, and a shared Go service used by both CLI and GUI.

## Work completed

### GUI product planning

- Defined the desktop information architecture and primary user flows.
- Defined setup, capture, Run detail, verify, restore, handoff, Store, sync, and
  operation experiences.
- Added explicit UI semantics for supported, experimental, degraded, blocked,
  failed, and unsupported states.
- Defined a sandboxed development mode so acceptance does not read or modify
  real Session Manager, Codex, repository, or Store data.

### Architecture planning

- Selected the stable Wails v2 line with React, TypeScript, and Vite.
- Rejected Wails v3 for the initial implementation because it remains
  alpha/pre-release at the planning date.
- Defined a shared typed service layer so CLI and GUI do not duplicate domain
  orchestration or safety policy.
- Defined capture/restore preflight plans with expiration and input revalidation
  to protect against time-of-check/time-of-use changes.
- Defined typed errors, an operation manager, sequence-based progress events,
  safe cancellation, pagination, size limits, and GUI security boundaries.
- Split implementation into five incremental phases with explicit exit
  criteria.

### Acceptance planning

- Added 17 acceptance scenarios covering initialization, read-only inspection,
  capture preflight, input changes, full capture, corruption detection,
  cross-repository restore, conflicts, native restore degradation, handoff
  claims, security blocks, file/SSH sync, cancellation, restart catch-up,
  accessibility, and production security.
- Defined an acceptance evidence template based on operation IDs, reports, and
  expected/actual digests.

### Phase 0 desktop preview

- Added a Wails v2 desktop module at `gui/`, isolated from the no-CGO CLI
  module.
- Added a React/TypeScript/Vite frontend with a responsive Overview,
  navigation, system health, Run catalog, Store status, active operation,
  quick actions, and a Capture preflight panel.
- Added an explicit Acceptance Preview mode. It uses fixture data and labels
  every preview surface so developers cannot mistake it for a real capture or
  restore.
- Added the first shared read-only Go service for Dashboard health, catalog
  summaries, recent Runs, Store summaries, and initialization.
- Connected the native Wails bridge to the shared service. The standalone
  frontend falls back to the same fixture contract for visual development.
- Added native directory selection to the bridge and left all mutating actions
  stopped at read-only preflight.
- Added frontend and service regression tests, GUI Make targets, dependency
  locks, and build-artifact exclusions.

## Decisions and rationale

- **Wails v2 before v3:** v2 is the current stable line and integrates directly
  with Go. v3 remains alpha/pre-release and will be reviewed again before GUI
  release packaging.
- **Wails v2.12.0 compatibility pin:** v2.12.0 supports the repository's Go
  baseline while preserving a stable v2 bridge. The GUI lives in a child Go
  module so Wails and native WebView dependencies cannot enter CLI builds.
- **Current frontend security pins:** Vite 8.1.5, React 18.3.1,
  TypeScript 5.7.3, and Vitest 4.1.10 are exact dependencies. The originally
  tested Vite 5/Vitest 2 spike was upgraded after `npm audit` reported known
  development-server vulnerabilities.
- **Shared service before screens:** current CLI command functions combine
  parsing, orchestration, reporting, and output. Extracting a service first is
  necessary to keep CLI and GUI behavior identical.
- **Desktop app rather than localhost UI:** this retains local-first behavior,
  reduces exposed attack surface, and provides native directory dialogs.
- **Preflight plus confirmation:** capture and restore are state-sensitive.
  Plans expire and inputs are revalidated before mutation.
- **Acceptance sandbox as a product-development feature:** GUI acceptance must
  be repeatable without risking real sessions, keys, Stores, or worktrees.
- **Evidence over visual success:** every mutation result exposes operation
  report and digest evidence. A green toast alone is not acceptance.

## Compatibility and migration

- This change does not alter manifest, normalized event, config, CLI JSON,
  Store, encryption, or catalog formats.
- Planned service extraction must preserve existing CLI flags, JSON shapes,
  exit codes, reports, and e2e behavior.
- Wails dependencies are isolated in `gui/go.mod`; CLI/Core remains separately
  buildable with `CGO_ENABLED=0`.
- The Dashboard service is an additive internal API with schema version 1. No
  persisted GUI state is introduced.

## Known limitations and risks

- The current GUI is a Phase 0 read-only preview, not a complete product. Runs,
  Stores, Operations, and Settings navigation pages are intentional
  placeholders.
- Capture, pull, verify, handoff, Store tests, restore progress, and Store
  values shown in Preview mode are fixtures and cannot mutate state.
- Real Dashboard mode reads local health, catalog, recent Runs, and configured
  Stores, but has not completed the acceptance scenario matrix.
- Linux WebView baseline and package format still require a clean-image spike.
- Actual SSH GUI flow depends on the pending disposable SSH fault-injection
  environment.
- The current backend has an initial shared read-only service but no persistent
  operation manager, capture/restore preflight plans, or service-level
  pagination.
- The Wails GUI will require a platform desktop/WebView toolchain. The existing
  CLI must remain a separately testable no-CGO build.
- Wails v2 will eventually be superseded by v3, so the bridge and frontend must
  remain thin enough to migrate.

## Next steps

1. Move CLI `Doctor` and `ListRuns` orchestration onto the shared service while
   preserving output, flags, and exit behavior.
2. Replace the Runs placeholder with catalog pagination, filters, and Run
   detail backed by verified service responses.
3. Add persistent operation records and Wails event delivery with reload
   catch-up.
4. Implement Capture preflight plans with expiration and input
   revalidation; keep mutation disabled until the acceptance fixture passes.
5. Create the isolated acceptance fixture generator and automate the first
   acceptance IDs.

## Addenda

### 2026-08-05 — product reset

The user determined that workspace/session synchronization duplicated the
existing Git workflow. v0.3.0-dev replaces this direction with a small Markdown
session exporter. The Wails/React source and its planning/acceptance documents
were removed; v0.3 later added a much smaller standard-library local GUI around
the exporter. This devlog remains historical evidence of the superseded work.
